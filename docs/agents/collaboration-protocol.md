# Agent 团队协作协议（dsh-session-toolkit）

**适用范围**：本仓库的功能开发、DSH 兼容跟进、工程化与发布。
**不适用范围**：与本仓库无关的通用任务。
**本文件的权威性**：低于 `README.zh.md` / `README.md` 与源码。任何冲突以代码与 README 为准，并回来修本文件。

---

## 1. 机制事实（先认清边界，再谈分工）

| 事实 | 含义 |
|---|---|
| 当前可用机制是**可继续 subagent**（`subagent` / `subagent_fork` / `send_message` / `list_agents` / `interrupt_agent`），按调用派生 | 「常驻」= 角色定义常驻，**不是**进程常驻 |
| 团队成员也可以是**独立顶层会话**（`list_sessions` / `send_to_session`），与 subagent 是两套并存机制 | 2026-09-10 首轮用的就是后者：4 个角色各是一个顶层会话，各有独立 GUI 窗口，**共享同一 workspace 路径** |
| 子 agent 与顶层会话**都看不到 Tech Lead 的对话**（`subagent_fork` 例外，它继承 Tech Lead 已完成轮次） | 每次派发必须自带完整上下文，不能指望"它知道" |
| 顶层会话之间的消息**可交叉**：双方在途互发时，任何一方都可能先收到对方更早的一条 | **「未回复」≠「未在途」**。处置见 §6.5。首轮实测出现 3 次交叉 |
| 所有成员**共享同一个工作区**，无 worktree、无文件锁、无合并 | **并行写同一文件 = 必然冲突**。这是本协议最重要的一条约束 |
| DSH 的**实验性 Agent Teams**（`ctx.agentTeams` + `spawn_teammate` / `team_task_*`）**当前未启用** | 启用需持久会话存储 + profile patch；且其限制同样是共享 checkout、无隔离、扁平 roster、无自动 ownership 释放、契约可变。**默认不开**，见 §9 |
| 同一时刻只有一个 Tech Lead 持有编排权 | 禁止多 agent 互相派发形成网状调用 |

## 2. 角色与所有权（5 个）

**写权是排他的**：一个文件族在同一时刻只允许一个写者。下表的五组写权两两不相交——这是缩减到 5 个角色时唯一不能妥协的性质。

**覆盖性（2026-09-10 修订）**：原表只保证了「**两两不相交**」（不冲突），**未保证「覆盖全仓库」**——`cordis.patch.yml`、`.gitignore`、`pnpm-lock.yaml`、`LICENSE` 四个文件曾处于**无主**状态。无主文件等于谁都能改、出事无人可追，且会被基线提交顺带入库。现已补齐到上表。
**由此确立一条规则**：**任何未列入上表的文件 = 无主 = 禁写**。需要动它，先由 Tech Lead 明确指派归属。

**读权是公共的（2026-09-10 修订）**：写权排他**只约束写入**；**任何角色都可以读任何文件**，包括 Tech Lead 的 `package.json` 与 `docs/agents/**`。§6.7 要求成员动手前读真源并附哈希——若把读权也当成受限，该规则根本无法执行。**不得以"那不在我文件族内"为由拒绝读盘或拒绝采信自己的读取结果；也不得采信他人转述，必须直接读盘。**

**补齐两处无主文件（2026-09-10）**：
- `.gitattributes` → **Tech Lead**（仓库级配置，与 `.gitignore` 同类）。**但「创建它」未获授权**：行尾归一化是**仓库级字节变更**（会让大量文件在下次 checkout 时改写），必须单独决策。在此之前，`.gitattributes` 缺位是一条**已登记的已知缺口**，记录在 `docs/agents/baseline-registry.md` §3.6。
- `cordis.patch.yml` 的 `config:` 载荷 review 钩子见本节上文（条件性，尚未触发）。

| 角色 | 写权（独占） | 职责 | 何时启动 |
|---|---|---|---|
| **Tech Lead**（技术负责人） | `package.json`、`docs/agents/**`、`cordis.patch.yml`、`.gitignore`、`LICENSE` | 拆解、派发、**串行集成**、最终审核、版本号、发布决策、保证 README 承诺 = 实际行为 | 全程（即主会话） |
| **Host Dev**（宿主端开发） | `lib/**` | host 半实现：settings 命名空间、系统提示词段、工具注册、生命周期绑定、`ctx.get` 判空降级 | 涉及 host 行为的改动 |
| **Client Dev**（客户端开发） | `client/client.js` | client 半实现：slot 注册/遮蔽、React 渲染、主题变量、i18n 字典、重启状态机、client 侧 schema 对齐 | 涉及 UI/交互的改动 |
| **QA Engineer**（质量保障工程师） | `scripts/**`、`.github/**`、`pnpm-lock.yaml`（对其余文件**只读**） | 三层验证与交付：维护验证门与 CI（L1）、核验集成点契约（L2）、独立验证与端到端冒烟（L3）、发布前核对 | DSH 升级、每次行为变更后、发版前 |
| **Tech Writer**（技术文档工程师） | `README.md`、`README.zh.md`、`README.i18n.yaml` | 双语 README 成对维护、版本引用、安装/配置说明、发布说明 | 行为变化需要对外表述时 |

角色名就是真实英文岗位名，并且**原样**用作派发字段与任务面板上的 id。选用 `Client Dev` 而非 `Client` 是刻意的：`Client` 作 id 会与目录 `client/` 在派发文本里撞车。

**为什么 `package.json` 归 Tech Lead 独占**：它同时是版本真源（`version`）、脚本真源（`scripts`）与打包真源（`files`/`exports`/`dsh`）。多个角色都想改它，冲突代价最高，故收归单一写者。

**为什么 `cordis.patch.yml` 归 Tech Lead、但要给 Host Dev 一个 review 钩子**：`package.json` 的 `dsh.bundle.patch` 指针与它成对，同属打包真源。但它**同时是 host 组合真源**：它 `insert` 的插件行若带上 `config:` 载荷，那份载荷会被 `lib/index.js` 的 `Config`（schemastery `z.object`）校验——而 `Config` 的写权在 Host Dev。
**review 钩子**：`cordis.patch.yml` 若新增/修改 `config:` 载荷，需 **Host Dev 核 `Config` 对齐后方可落盘**。理由：`Config.client` 的分键必须与 `client/client.js` 的 `ClientConfig` 双写同步（`lib/index.js:35` 注释明写），而 `config:` 载荷是这些键的**第二个入口**；schema 里不存在的键在严格对象校验下会被剥离或报错，属「静默失效」型故障。
（当前该文件仅 5 行、无任何 `config:` 载荷，故此钩子是**条件性**的，尚未触发。）

**为什么 `QA Engineer` 值得信任**：它是 `lib/**` 与 `client/client.js` 的**非作者**——这是独立性要求的实质。
残留风险：同一角色既造验证门又使用验证门，属自证。补偿控制三条：(1) 改动验证门必须附负向测试并交 Tech Lead 审；(2) 门变动的证据以**命令退出码与原始输出**为准，不接受判断性结论；(3) Tech Lead 保留推翻权，且必须书面记录未消除的风险。

**已知代价（Tech Lead 需盯）**：`QA Engineer` 吸收了原编制里 4 项职责，是全队唯一的瓶颈角色。若 DSH 升级与功能开发同时压上，第一个该拆回来的就是它——优先把「契约核验」拆成独立只读角色。

## 3. 派发契约（Tech Lead 每次派发的必填项）

子 agent 没有共享上下文，派发必须自带：

```
[角色]        Host Dev / Client Dev / QA Engineer / Tech Writer
[目标]        一句话，可验收
[涉及文件]    精确路径；写者只能拿到自己文件族内的路径
[硬约束]      冻结设置铁律、不调 dispose()、不动其它文件族、不动 README 承诺之外的行为
[验收标准]    可执行的判据，不是"看起来对"
[证据格式]    命令 + 原始输出（不许只给结论）
[禁止事项]    明确列出（例如"不要顺手重构"、"不要改版本号"）
```

**派发前的自检**：这条派发里，写者是否只有一个文件族？如果不是，拆开串行。

```
## 变更摘要
<文件 → 行为变化>，逐条，不超过 8 条

## 证据
$ <实际执行的命令>

## 未决与风险
<没做的、没验证的、不确定的、需要人决策的>
```

缺任一段视为未完成。

## 5. 验证分层

| 层 | 内容 | 命令 / 手段 | 负责 |
|---|---|---|---|
| **L0** | 语法门 | `pnpm check` | 任何写者自测 + `QA Engineer` 复核 |
| **L1** | 打包契约（入口可达、import 声明完整、双语 README 版本一致、「本包当前版本」定向断言） | `pnpm verify` | `QA Engineer` 维护与复核 |
| **L1s** | 验证门自测：**证明门自身能报红**（24 条 = 1 控制 + 19 报红 + 4 路径契约） | `node scripts/verify.selftest.mjs` | `QA Engineer` |
| **L1c** | 特性契约门：启动恢复在**两种 `list()` 形状**下都选对目标；未识别形状必须留可诊断告警 | `node scripts/auto-resume.contract.selftest.mjs` | `QA Engineer` |
| **L2** | 集成点契约（对照 harness 源码） | `docs/agents/integration-contracts.md` §D 的抽取命令 + 逐行核 | `QA Engineer` |
| **L3** | 端到端（安装 + GUI 冒烟） | `dsh plugin --profile web add <本仓库路径>` → 重启 GUI → 用 `browser-skill` 走一遍受影响路径 | `QA Engineer` |

**铁律**：
- 涉及 host/client 行为变更的改动，**L0+L1 必须在 Tech Lead 集成前跑绿**；只碰文档/脚本的改动可只跑 L1。
- **不会失败的检查等于没有检查**。新增任何检查，必须附一次负向测试（故意破坏 → 确认它报红 → 复原）。**「零命中」「全绿」这类负结果，必须先证明该检查能报红才可信**——不做阳性对照的负结果等于没有结论。
- **验证手段本身必须先被验证**：任何用于判定通过/失败的工具、指纹或对照方式，必须先证明它 (a) **能报红**，且 (b) **不改变被测对象**。2026-09-10 首轮实测出现三例仪器缺陷，全部来自「手段未验证」：
  1. 用「工作树 + `.git` 状态」整体指纹做跳变检测 → `git status --porcelain` 每次调用都会改 `.git` 目录 mtime（短暂建删锁文件），产生**观测者效应**，差点报出假警报；
  2. 用 `Get-Content` 读 UTF-8 中文注释扫同形字 → 本机是 Windows PowerShell 5.1，默认按系统 ANSI（GBK）解码，UTF-8 字节落进西里尔区，**27 个命中全是假阳性**；
  3. 用 `Set-Content -Encoding utf8` 造破坏用例 → 5.1 上写 BOM，`JSON.parse` 抛 `\ufeff` 使 4 个用例的 `exit=1` **来自解析失败而非被测检查**，即「退出码 1 ≠ 检查生效」。
  4. 用 `Get-Content` **数行**或**读含中文的文本** → 5.1 默认按 ANSI（GBK）解码，多字节序列吞掉换行，**行数偏小、内容错位**；同一文件实测得出 112 与 187 两个"行数"（另一次 114 vs 138）。**前三例与本例同根因：默认编码。**
- **明令禁止（编码类仪器）**：在 Windows PowerShell 5.1 上，**不得**用 `Get-Content` 数行、读含中文的文件、或生成指纹。数行与读文本一律 `[IO.File]::ReadAllLines(<path>, [Text.Encoding]::UTF8)`（或 `ReadAllText`）；哈希一律 `Get-FileHash -Algorithm SHA256`（二进制，与编码无关）。**违反本禁则得出的任何数字都不是证据——无论它与谁的数字吻合。**
- **假绿比缺检查更糟**：任何「跳过」都不得在退出码或输出上被读作「全部通过」。跳过必须是**可区分的状态**，不能与通过同形。
- `pnpm verify` 的 `pack` 模式断言「工作区内容 == 包内容」。若有人给 `package.json` 加了 `prepare`/`prepack`/`prepublishOnly`，脚本会主动报错——这是设计意图，别绕过它。
- **两个自测门（L1s / L1c）不进 `pnpm verify`**（保持快门快），由 CI **独立 job** 调用；`publish-npm` 的 `needs` 同时依赖三者。**理由：门不可信时，门给出的绿也不可信**——所以发布必须同时被门与被"门自身能报红"这件事拦住。
- **契约门必须按契约判别，不按代码身份判别**：`L1c` 里旧代码在「裸 header 形状」那条应 **PASS**，红只出现在契约真的被违反的两条。若有人把它改成「凡 HEAD 那份就报红」，那是把契约断言偷换成代码指纹断言，**判为回归**。

## 6. 裁决与升级

1. 分歧一律以**可执行证据**裁决；不以"多数意见"或角色层级裁决。
2. `QA Engineer` 的否决只有在**给出反例证据**时成立；Tech Lead 若推翻，必须在交接物里写明理由与未消除的风险。
3. 无法靠证据裁决的（产品取舍、发布时机、是否动 DSH 实验特性）→ **升级给人**，不猜。
4. 同一阻塞条件连续 3 轮未解决 → 标阻塞并上报，不重复空转。
5. **裁定编号**：Tech Lead 每条裁定带序号。成员按收到的**最高序号**执行，并在回执里写明「执行的是裁定 #N」；编号不明时按最高序号执行，同时指出潜在冲突。**目的**：顶层会话之间的消息会交叉（§1），编号使一次交叉只产生**一次澄清**，而不是**一次返工**。首轮实测因缺此机制产生 3 次交叉返工。
6. **基线对拍口径**：只比**内容**——`git status --porcelain` 文本 + 逐文件 blob 相等（`git rev-parse HEAD:<path>` == `git hash-object <path>`）；未跟踪的承重件用内容 SHA256；**永不把 `.git` 目录 mtime 纳入判据**（`git status` 自身会改它）。登记处与使用规则见 `docs/agents/baseline-registry.md`。
7. **真源读取须附哈希**：成员动手前读 `docs/agents/**`，并在回报里附上所读文件的 SHA256，供 Tech Lead 与登记处比对。不一致即停手报告——真源漂移必须在**使用点**被抓到，不能只靠某个人「开工前读一次」。

## 7. 反模式（明令禁止）

- 两个写者同时改同一文件族（尤其 `client/client.js`，它是 109KB 单文件，合并冲突几乎不可解）。
- 用 `subagent_fork` 做验证——它继承 Tech Lead 的上下文与盲点。验证要用**全新会话 + 只给它 diff、验收标准与证据要求**。
- 子 agent 顺手重构、顺手改版本号、顺手更新 README 里未涉及的段落。
- 无证据的"已完成"结论。
- 把 README 当需求文档：README 是**承诺**，改动若使其失真，必须同轮修文档或明确记为偏差。
- 让 `QA Engineer` 直接改源码——它只对 `scripts/**`、`.github/**` 有写权，对 `lib/`、`client/client.js`、README、`package.json` 一律只读；发现的问题写成报告交 Tech Lead 落。

## 8. 什么时候不派团队

满足任一条即**直接由 Tech Lead 做完**，不入队：

- 单文件小改、改文案、改注释、bump 版本。
- 影响面在 1 个文件族内且无需独立验证。
- 需求本身还没澄清（先澄清，再决定要不要建队）。

派团队的前提是：**存在可并行的独立工作面 + 存在可执行的验收信号**。两者缺一，团队只会加速产生不可验证的 diff。

## 10. 证据与协作纪律（2026-09-10 首轮实操定型）

**来源声明**：以下每一条都由首轮的**实际事故**换来，不是推演。事故记录见 `round-1-report.md` 与 `baseline-registry.md`。**它们是本协议最贵的部分**——每条都对应一次真实的假警报、假通过或返工。

### 10.1 治理与变更
1. **协议变更须广播并附哈希**：任何**改变义务**的协议/契约改动，必须广播给四个角色并附变更后文件的内容哈希。默认广播；若判断某次改动不改变任何义务而不广播，**必须当场声明"这次不广播"**——不许沉默跳过。
   **广播必须是同一份内容发给四个角色**；按收件人定制内容**不算广播**（2026-09-10 实测：Tech Lead 按各自贡献定制后，两个角色只收到部分条款，而它们无从察觉）。**若广播文本是摘要而非全文，必须在广播中明示「本文为摘要，权威文本以哈希锚定的文件为准」**——否则省略若落在义务句上，收件人会拿到一个与文件不同、**看起来却一模一样**的规则集。
2. **不得在派发进行中生效**：协议变更一律延到下一轮生效，避免规则**追溯适用**。
3. **冲突须当轮二选一**：Tech Lead 的口头指令与协议冲突时，Tech Lead 必须在**同一轮内**给出「改协议」或「撤指令」二选一，不许挂着。**协议 > 口头指令**：成员按协议执行，并**立即报告冲突**——沉默地二选一才是越界。
4. **治理条款须自检对作者是否有效**：任何治理条款落地前，必须先回答「**它对条款作者本人是否构成约束？**」若否，缺口在哪、由什么控制补上。**否则等级序形式成立、实质归零。**
5. **写权排他、读权公共**（§2）。

### 10.2 证据
6. **可信域 = 两个独立来源的吻合**。任何**单侧陈述**都不是证据——**包括 Tech Lead 的转述与成员的重述**。"我复核过原文"若是重述而非当场读取，不算证据。
   **「独立」的定义是「方法独立」，不是「执行了两次」**：两条读数若走**同一条读取/计算路径**，只算**一个**来源——哪怕由不同的人、在不同的时间各跑一遍。实测反例：Tech Lead 曾以「83 = 83，独立复核通过」自称双源吻合，而两次都走 `Get-Content`，共享同一 GBK 缺陷，**该结论已撤回**。
   **判据**：两条路径必须能**各自独立地报红**（即彼此不共享失效模式）；若无法指出失效模式如何不同，则按单侧陈述处理。
7. **判据是「取值时点与盘上是否一致」，不是「与最终产物是否一致」**。合规形态：标注**编辑轮次 + 取值时点**，并在**同一线程**后续消息中**显式作废**被取代的值。**只有「同一时点取值与盘上不符」才判不实。** 否则理性策略会变成"拿到值先压着不报"，把交叉从一次澄清恶化为延迟报告。
8. **身份值只在定稿后外发**：哈希/blob/字节数只在产物**已由带编号裁定定稿**后才发给下游对拍对象；外发须标注**是否可能受未决裁定影响**；作废必须与改动**同轮就地**声明。
9. **哈希程序化取值、原样粘贴**（禁手打、禁转述、禁插分隔符）。**长度/字符集校验仅作粗筛**，不得作为采信依据——**采信判据是当场在来源文件上重算并与登记值 MATCH**。抓不到单字符错的校验不是校验。
   **禁止缩写（2026-09-10 实测补充）**：外发一律给**完整 64 位十六进制**。`前8…后N` 这类缩写**本身就是转述**，且后缀长度不固定会让对拍方的定长切片逻辑**构造性失败**——实测：Tech Writer 按 `Substring(56,8)` 比对，四值全 DIFF，**错在格式，不在其比对逻辑**。若确需给人读的缩写，**必须同时给出完整值**；缩写只作显示，**不得作为对拍输入**。
10. **测量与写入串行**：登记任何身份前，必须确认**该写者的全部文件族**均不在写入窗口内（同一写者可有多个族）。**全工作区内容检查（如 `verify.selftest.mjs`）的运行窗口是全局互斥区**——任何写者，**包括 Tech Lead**，在该窗口内写入都会使它失败且结果不可归因。
    **§六 的核验读取同样是测量**（不只是「登记」）：与写入窗口重叠时读到的是**中间态**。此时**必须报告为「不确定」，不得据此下结论**，**不得重读追逐移动目标**（§10.2-7）——正确形态是**写者停手并给出定稿身份值**，读者再重读。实测：Tech Writer 在 Tech Lead 两次写入之间读全文，得 `total 135` 行而定稿为 **148** 行；其「报告不确定 + 不追移动目标」的处置**即为合规形态**。
11. **登记的关闭条件 = 三方一致**：①成员报告值 ∩ ②Tech Lead 当场重算 ∩ ③**成员明确停手声明之后**的再次重算。**「回执」不是停手信号**（实测被证伪）。**宣布交付之后的任何写入，必须先声明「我恢复写入」。**
12. **不得在没有判别探针的情况下把字面量分歧归因于消息通道**。要归因，先做对照实验，且必须满足：**无声明 + 不可猜构成（阳性对照）+ 双向 + 结论口径先写死**。

### 10.3 对等质疑与审计的执行标准
**被判定方反驳的合规模板**（首轮两次由 Tech Writer 给出，质量最高）：**列出可能性 → 用可查标识（消息编号、时点）逐条排除竞争解释 → 指出规则自身的不可满足边界 → 给出可执行的替代形态。**
**审计者的合规模板**：无指派地读真源 → 逐项对盘 → 分别报告一致/不一致 → 明示「我的报告不是基线来源」→ 声明自己的能力边界（**包括"我不盲"这类对自己不利的声明**）。
**实质要求**：成员**拒绝对自己有利的归因**，与拒绝不成立的判罚**同等重要**；Tech Lead 必须**能被判错**，且判决必须留痕。**没有任何外部压力时做出的自我更正，是这套机制里最不可替代的信号。**
